## 1. 项目目标

构建一个面向社区内容的检索与分析助手。用户用自然语言描述目标，Agent 将问题组织成查询、采集、筛选和分析步骤，最后提供可追溯到原文的回答。

MediaCrawler 负责获取数据；Agent 负责选择能力和组织步骤；Harness 负责执行控制、上下文、预算与证据约束。

首个目标平台为百度贴吧，先利用现有 `cs`、`cs饰品` 采集数据验证完整流程，再扩展到其他平台。

### 能力边界

- 若候选内容仍来自贴吧搜索，无法保证发现贴吧没有返回的帖子。
- 可以通过多种查询表达、结果合并、本地筛选和本地检索改善使用体验。
- 可以结合指定帖子、作者主页，以及项目支持的指定贴吧采集，减少只依赖关键词搜索的情况。
- 搜索命中不代表主题相关；评论属于命中帖子，也不代表评论本身包含查询词。
- “当前采集数据中没找到”不能表述成“平台上不存在”。

## 2. 现有基础与目录安排

现有基础包括 MediaCrawler 的平台采集能力，以及本地改造后的任务记录、独立文件保存、预览、筛选、导出和删除功能。

目前的关键词标签表示分别搜索；`source_keyword` 表示搜索来源，不是原文命中证据。原始数据和任务管理不应被模型分析结果覆盖。

建议在外层增加新模块，尽量减少对上游爬虫核心的修改：

```text
community-agent/
├── MediaCrawler/       # 现有采集项目与 Web 界面
├── src/community_research/
│   ├── agent/          # 已有：Harness、模型适配、采集调度
│   ├── knowledge/      # 已有：导入、来源、条件检索与证据读取
│   └── api/            # 已有：助手服务入口
├── docs/               # 设计与实施文档
└── testresult/         # 现有人工检查样例
```

以上为当前模块安排，不据目录结构断言保留独立 Git 历史。新增语义索引和任务策略应接入现有模块，不另建一套脱离 Harness 的助手。

## 3. 整体工作流程

```text
自然语言问题
    ↓
结合会话理解目标，判断任务类型、时效与证据需求
    ↓
检查本地内容的覆盖与新鲜度，决定本地、联网或组合执行
    ↓ 在默认预算及用户自然语言限定内自动执行
需要时生成有限查询，联网发现候选帖子
    ↓
去重、字面匹配、主题相关性判断
    ↓
对选中的帖子补采正文和评论
    ↓
建立帖子—评论关系与证据索引
    ↓
生成带引用的回答，展示覆盖范围
```

### 示例问题

> 找最近一个月讨论 CS 饰品价格下跌的帖子，重点看下跌原因和玩家反应，排除无关的人际纠纷。

助手整理出：

- 主题：CS 饰品价格下跌。
- 候选查询：`CS 饰品`、`CS2 饰品 降价`、`反恐精英 饰品 崩盘`。
- 时间范围：最近一个月，并明确对应日期范围与时区。
- 证据需求：帖子正文和相关评论。
- 排除条件：主要讨论其他话题，只顺带提到打 CS 的内容。
- 预算：查询数量、帖子数量、每帖评论数量、总时限和模型调用上限。

上述内容由助手内部规划。正常对话仅显示简短进度，在默认预算内直接执行，不要求用户查看或确认关键词表单。用户通过“多找一些”“只看最近一周”“重点看评论”等自然语言调整需求；具体参数可在执行详情查看。平台不支持的时间或筛选条件可在本地处理，但必须说明这不等于平台范围内的完整检索。

## 4. 先发现帖子，再深入采集

避免一开始就对全部搜索结果采集评论：

1. 通过多组查询获取候选帖子和可用正文。
2. 按平台和帖子 ID 合并重复候选，保留各个查询来源。
3. 判断标题、正文与目标主题的关系。
4. 对相关或待确认的帖子使用指定帖子模式补充采集。
5. 根据问题决定需要多少评论、是否采集子评论。

| 现有能力 | Agent 中的用途 |
| --- | --- |
| Search Mode | 用不同表达发现候选帖子 |
| Detail Mode | 深入采集已经选中的帖子及评论 |
| Creator Mode | 问题涉及某位作者时，补充其发布内容 |

作者模式不等于能够获取该用户在整个平台发表的全部评论。

### 查询扩展与目标保持

扩展的是寻找目标的表达方式，不是让目标随着关键词含义变化。方案采用以下原则，具体阈值和预算分配仍需样例验证。

以用户要找 donk 这位 CS 职业选手为例，“小驴”可以成为待核对的查询表达，但不能由此把任务转成寻找动物、养殖或农牧业信息。

每个研究任务应保存独立于查询词的目标记录：目标人物或主题、领域语境、用户希望回答的问题、时间范围，以及用户明确提出的限制。只有用户修改需求或确认澄清结果时，才更新目标；模型生成的新查询不能直接覆盖它。

如果用户仅输入“小驴”，且没有足够上下文区分选手与动物，应先澄清。如果此前对话已经明确目标是 donk，则沿用该目标，不必重复询问。用户提供的称呼作为线索保存，不自动视为唯一、永久有效的别名。

### 主线检索与有限探索

| 分支 | 适用内容 | 执行方式 |
| --- | --- | --- |
| 主线检索 | 明确名称、有证据支持的别名、较强关联的事件 | 优先分配预算，获取主要证据 |
| 有限探索 | 高歧义称呼、新梗、间接指代、可能相关的主题 | 小批量试探，先验证关联再决定扩大范围 |

每次扩展记录原始目标、来源查询或证据、拟用表达、关联理由、歧义和本轮预算。人物别名与主题入口分别标记：例如榜单可能包含目标人物，不等于榜单就是该人物的别名；词语共现也不等于指代同一个人。

结果返回后核对与目标的联系，依据新增相关内容、重复比例和成本决定继续、缩小查询、换表达或停止分支。探索不得自动递归扩张；缺少关联证据时保留为待确认，不作为已核实结论。连续低收益或预算耗尽时停止，并说明覆盖不足，而不是宣称找全了。

领域语境可以来自正文、贴吧名称、原帖、父评论等，不强制每条相关内容都出现“CS”。如果平台不支持领域过滤，组合查询“小驴 CS”也不能保证平台严格执行；本地验证仍然必要。

## 5. 分开记录来源、命中与相关性

| 信息 | 示例 | 意义 |
| --- | --- | --- |
| 搜索来源 | 通过 `cs饰品` 找到 | 说明采集过程 |
| 字面命中 | 正文出现 `cs` 和 `饰品` | 说明实际文字匹配 |
| 主题相关性 | 主要讨论饰品价格 | 说明是否符合用户目标 |

### 规则筛选

支持同时包含、任一包含、排除词、时间范围，并明确匹配对象：标题、正文、评论或其组合。

例如“同时包含 `cs` 和 `饰品`，位置不限”应作为明确的本地筛选条件，不依赖贴吧对一个搜索标签的解释。

只检查实际内容字段，不把 `source_keyword`、任务名称或模型生成的说明当作命中依据。记录命中字段和原文片段。

### 模型筛选

对规则难以判断的主题相关性，由模型输出：

- 相关、不相关或待确认。
- 简短理由。
- 支持判断的原文片段及其证据 ID。

不得用模型判断替换原始内容。筛选作为独立标记保存，允许人工检查误判。

### 评论筛选

提供三个视图：全部已采集评论、字面匹配评论、主题相关评论。没有关键词的评论也可能依赖上下文讨论同一主题，不能一律删除。

## 6. 本地数据与检索层

保留任务输出文件作为原始快照，在其上建立统一索引。

| 数据对象 | 主要字段 |
| --- | --- |
| 帖子 | 平台、帖子 ID、标题、正文、来源链接、发布时间 |
| 评论 | 平台、评论 ID、所属帖子 ID、父评论 ID、内容、发布时间 |
| 采集任务 | 任务 ID、查询参数、时间、状态、范围和数量限制 |
| 来源关系 | 内容与采集任务的关联、查询词、采集时间、快照位置 |
| 分析记录 | 规则版本、模型判断、命中片段、证据引用 |
| 检索目标 | 目标人物/主题、领域语境、用户问题、约束、目标修订记录 |
| 查询分支 | 所属目标、主线/探索类型、来源证据、关联假设、预算、结果与继续/停止原因 |

同一帖子可以维护统一检索入口，同时关联多个任务，保留各次快照和来源。评论通过所属帖子 ID 关联正文，子评论通过父评论 ID 保留回复关系。

已有关键词检索和明确的“且／或／排除”条件。P5已接入小规模关键词＋向量混合检索，并于2026-09-24配置本地中文嵌入模型；当前只验证链路可用，具体质量阈值仍需独立标注评测，细节见第12节及[P5交付说明](p5/README.md)。语义相似不直接作为事实匹配或实体别名确认。

本地检索可以支持：

> 在已采集数据中，哪些帖子同时提到 CS 和饰品？哪些评论认为价格下跌与更新有关？

## 7. Harness 与统一工具接口

### 建议工具

| 工具 | 职责 |
| --- | --- |
| 查询本地帖子 | 根据条件返回帖子与命中片段 |
| 查询本地评论 | 根据帖子、内容条件等返回评论及关联信息 |
| 创建采集任务 | 将采集计划转换为受限制的 MediaCrawler 任务 |
| 查看任务进度 | 返回状态、数量、错误和覆盖范围 |
| 读取证据 | 根据 ID 获取正文或评论片段 |
| 执行相关性筛选 | 保存独立的规则或模型判断 |
| 导出结果 | 导出选定数据、来源和分析结果 |

工具接口应有明确的参数、结果结构和错误类型，模型只能调用已注册工具。读取、采集和删除等不同影响范围的能力分别控制；数据删除默认保留在用户界面操作，不由模型自行决定。

### 运行控制

- 限制总时限、模型调用次数、查询数量、帖子与评论数量。
- 支持取消，工具失败有限重试，避免无限循环。
- 区分参数错误、登录需求、网络错误、平台拒绝、部分结果与无结果。
- 保存可检查的执行过程，不记录 Cookie 等登录凭据。
- 用户在本地完成扫码或其他登录验证，Cookie 不进入模型上下文。
- 将采集内容视为不可信数据，帖子中的指令不能改变系统规则或触发额外操作。

### 提示词、工具与 Harness 的职责边界

| 层次 | 职责与边界 |
| --- | --- |
| 提示词 | 引导模型保持目标、生成候选表达、说明关联依据；不能单独保证不发生语义漂移 |
| 检索工具 | 接收结构化的查询和条件，报告实际执行范围、结果及不支持的条件 |
| Harness | 持久保存原始目标和分支记录，校验参数与预算，控制扩展、停止和用户确认后的目标修订 |
| 结果核验 | 结合原文及上下文判断关联是否成立；必要时进行人工核对 |

Harness 可以要求扩展必须携带关联依据，并强制执行预算，但不能仅凭结构校验保证依据真实或语义判断正确。证据存在性与关联判断应分开检查，不能把模型填了“相关”字段就当作验证通过。

### 回答约束

每个实质结论应关联实际读取的证据，回答说明采集时间和范围。部分采集不得声称完整覆盖，用户评论中的陈述应按其来源表达，不能自动当成已经核实的事实。

## 8. 面向问题和证据的页面

目标是一个干净的助手入口：输入问题、简短进度、回答与停止操作。不新增口碑/趋势等任务按钮，移除正常流程中的“查询已有数据/联网采集”选择及“等待确认”的参数卡。默认范围与预算由系统执行，用户通过对话调整；模型分类、查询词和分支参数放在可展开详情。原手动爬虫作为高级备用入口，不是正常任务的必经步骤。2026-09-21已完成这些交互移除和默认执行基础，语义质量仍单独验收。

保留现有数据管理，并增加问题、采集任务、结果与回答之间的关联：

- 一次提问可以关联多个查询和采集任务。
- 帖子卡片显示标题、摘要、搜索来源、命中片段和相关性理由。
- 展开帖子后查看评论和回复关系，切换不同筛选视图。
- 助手回答引用跳转到本地对应帖子或评论，并提供原站链接。
- 从证据页面返回时保留对话、助手输出、选中任务和筛选状态。

本地评论页面可以实现精确定位和高亮。外部贴吧是否支持直接定位某条评论，需要单独验证；不能保证外部链接具有原自建社区相同的定位行为。

## 9. 实施阶段与验收

### 第一阶段：本地数据助手

交付：导入现有任务文件、建立帖子与评论关系、条件检索、证据阅读、带引用回答。

验收：

- 同一记录可追溯到原始文件和采集任务。
- `source_keyword` 不参与正文命中判断。
- 能解释一条结果为什么出现，并区分搜索来源和实际命中。
- 评论引用可以返回所属帖子，同一帖子跨任务的来源不丢失。
- 未采集或未命中的内容明确说明范围，不作全平台不存在的断言。

### 第二阶段：Agent 调度采集

交付：自然语言查询计划、多查询执行、任务等待、候选去重、指定帖子补采评论。

验收：

- 查询计划和预算可追溯；按最新目标通过自然语言调整，默认预算内不出现必经的配置确认卡。
- 实际参数与计划一致，不静默回落到示例关键词。
- 取消和超时能终止工作，失败不会被误报为无结果。
- 一个问题关联的多个采集任务可在界面中追溯。
- 查询表达变化不会覆盖原始目标；只有“小驴”且缺少上下文时会澄清，已明确 donk 的会话不会因该词自动转向农牧业。
- 每个探索分支有来源、关联假设和预算，低收益分支能停止，用户修订目标可追溯。

### 第三阶段：相关性与分析

交付：模型相关性判断、语义检索、主题归纳，以及需要时的增量采集和比较。

验收：

- 使用人工标注样例比较原始搜索与改进后的相关结果比例。
- 单独检查误删的相关结果，避免只追求减少无关结果。
- 抽查回答引用是否支持结论，检查模型是否把评论观点当成事实。
- 记录耗时、模型用量和采集量，比较改进效果与成本。
- 使用歧义称呼、多人比较和跨领域噪声样例检查目标漂移；同时检查仅凭父评论或贴吧语境关联、没有出现“CS”字样的有效内容是否被误排除。

## 10. 优先顺序

历史实施顺序为先本地数据与证据，再接入采集；当前已具备P4最小闭环。下一步优先完成自动任务与数据来源判断、默认预算执行，再逐项验证有限扩展、混合检索和评价分析。

第一阶段不同时引入多 Agent、大规模平台覆盖、复杂调度系统和向量数据库。每一阶段先形成可检查的闭环，再扩展能力，避免功能堆叠后无法判断错误发生在哪一层。

## 11. 顶层任务规划

初始规划日期：2026-09-20；2026-09-21修订。P0—P4最小闭环已实现；P5现为部分实施，具体进度见本节各阶段状态。现有爬虫和任务数据管理继续复用，不列为新交付。以下“第一版”描述历史阶段范围，不限制最新目标。

### 11.1 首版范围

首个可用版本交付“本地贴吧数据助手”：用户提问后，助手能查询已采集帖子和评论，给出带原文引用的回答，并从证据页返回原对话。

范围约束：

- 首先接入现有贴吧 JSON/JSONL 样例与任务文件；其他平台和格式按后续需求扩展。
- 原始文件保留；索引和分析结果单独存储，不修改原始采集内容。
- 模型通过适配接口接入，不训练基础模型；实际供应商、密钥和模型能力在模型接入阶段核对。
- 第一版不自主访问平台，不实现自动别名发现、多 Agent、向量数据库或分布式调度。
- 从第一版就保存目标、证据和执行预算，避免后续采集调度时重新拆改核心流程。

### 11.2 模块边界

| 模块 | 负责 | 不承担 |
| --- | --- | --- |
| 采集适配层 | 封装现有 MediaCrawler 的启动、状态、取消和结果导入 | 不决定研究目标，不自行改变查询意图 |
| 数据与检索层 `knowledge/` | 规范化、来源关系、快照、索引、条件检索、证据读取 | 不让模型直接执行 SQL 或修改原始数据 |
| Agent 与 Harness `agent/` | 目标与会话、模型适配、工具注册、调用循环、预算、事件记录 | 不直接包含各平台爬虫逻辑 |
| 相关性策略 | 字面条件、语境核验、候选别名和探索收益判断 | 不把模型相关性分数当作已验证事实 |
| 服务与界面 | 提问、进度、结果筛选、证据查看、会话恢复 | 不在界面中重复实现检索和权限规则 |
| 评测与诊断 | 固定样例、故障用例、引用核对、用量统计 | 不仅凭演示成功判断质量 |

第一版优先复用现有本地 Web 服务和页面入口。P0 阶段确定外层 Python 模块的加载、依赖和测试方式，避免依赖临时修改工作目录才能运行。此处先固定职责，不提前展开文件级类设计。

## 12. 最新需求：单一助手与内部自动判断（2026-09-21）

### 12.1 交互与决策原则

用户描述目标，不负责选择工具、制定关键词或填写采集配额。即使把配置改成两个按钮，仍然是在把系统决策交给用户，不符合本次明确的方向。

内部流程为：问题＋会话上下文 → 结构化任务规划 → 检查数据覆盖与新鲜度 → 在默认预算内选择检索/采集/分析 → 核验证据并回答。任务可以组合，不强制只落入一个分类；模型产生策略，Harness校验工具、预算和目标一致性。

| 用户表达 | 内部策略示例 |
| --- | --- |
| 找提到donk的帖子 | 内容查找、有限表达扩展、逐条返回来源 |
| 某游戏最近在玩家群体里评价如何 | 时效判断、多方向采样、评价识别、分歧与原因归纳 |
| 更新前后态度变了吗 | 匹配时间窗口与来源范围后比较；不可比时明确说明 |
| 为什么很多人在骂这次更新 | 先验证前提，不把提问中的“很多人”直接视为事实 |
| 刚才这些帖子说明什么 | 优先当前会话证据，按需重读，不默认重新采集 |
| 收集贴吧一些热门的打分帖 | 生成打分帖/打分贴/评分帖等候选表达，核验主题并按可用热度字段筛选 |

“最近”通常需要检查新鲜度，但不等于每次必须联网；本地已有足够新且合适的数据可复用。“只看已采集内容”等用户约束优先，不能为补足证据擅自联网。遇到关键对象不明、需要登录或超出授权范围时才打断，普通分类和参数选择由助手完成。

讨论中的首版建议值如下，**是待落实的默认策略，不是对当前代码默认值的描述**：

| 预算项 | 建议默认上限 |
| --- | --- |
| 查询分支 | 每轮最多3个 |
| 候选帖子 | 全轮合计20个，不是每查询20个 |
| 补采评论 | 按需最多3帖，每帖20条一级评论 |
| 总时限 | 180秒，包含规划、登录等待、采集和回答 |

这些值是上限，不必用满；模型调用、重试及总请求也需要服务端硬上限，具体数值和总时限核算随实现确认。跨分支重复抓取仍消耗请求预算，去重不能让实际工作量绕过限制。

“多找一些”允许助手在系统硬上限内适度扩大，并说明实际范围；“最近三个月”调整时间条件，不自动等价于增加数量；“重点看评论”调整证据分配；“继续”结合上轮目标及已获得内容，避免机械重复采集。超限不能静默无限放宽；说明限制，必要时再询问。用户可以随时停止。

不再默认显示“在线采集·等待确认”、查询词输入框和数字参数表。例行计划通过一句进度说明表达，参数留在执行详情。历史待确认计划不因改版、刷新或重启自动运行；用户的新请求才能触发新执行。

### 12.3 提问式检索与评价分析

“关于某游戏的内容”不等于“对该游戏的评价”。仅以游戏名检索会得到攻略、组队、交易等内容；用户无需编写更复杂的提示词来弥补这一差别，任务规划应从问题中识别证据需求。

评价分析按玩法、更新、性能、付费、运营等候选方向组织小批量查询，再根据真实讨论修正方向。同时保留少量宽泛查询，发现未预设的议题，避免只搜“差评/退坑”制造负面样本。帖子不是评价类，也可能包含有价值的评价评论，须结合上下文判断。

相关性与评价立场分开标注：相关内容不一定表达态度，负面态度也不意味着无关。识别赞同、批评、混合、未明确及反讽等不确定情况，保留支持片段，不强行二分。去重并注意同帖大量回复、重复转述和活跃用户造成的偏差；身份信息不足时不能推断独立玩家人数。

总结维度包括受到认可的方面、争议问题、原因和意见分化。只能归纳实际采到的时间与社区范围，不把贴吧便利样本称为全体玩家民意；没有充分、可比的样本时不输出貌似精确的总体好评率或趋势。

### 12.4 语义向量与有限扩展的分工

先保留字面检索，再为已采集帖子与评论建立语义索引，按问题进行混合召回、合并去重和少量候选核验；切片必须保留所属帖子、父评论、原文位置及快照来源。嵌入模型版本和失效清理需可追溯，源文件删除后不能通过向量结果继续引用失效内容。

向量检索可以帮助将“价格下跌原因”与“库存抛售/市场恐慌”这样的不同表达联系起来，但只覆盖已进入索引的内容，不能找回平台从未返回的帖子。向量相近也不能证明“小驴”就是donk。候选发现仍需有限查询扩展，别名映射仍需领域、时间和原文依据；宽泛描述和HLTV榜单等主题入口不能混同于别名。

### 12.5 “热门打分帖”的验收例子

不能把输入需求缩成一个“打分贴”关键词就视为理解完成。应核对帖子类型、适度尝试常见写法，并在采到的候选中比较回复量、发布时间等可获得信息。回复数为采集时统计，不等于独立参与人数或正面评价；字段缺失不能补成0。若只有按时间排序的搜索结果，应明确候选发现限制，不能将本地排序称为全站热榜。

### 12.6 新增验收要求与未定事项

- 单次自然语言提问无需选模式、填查询词或确认表单，能完成默认预算内的任务；仍可查看过程和停止。
- 本地足够新、数据陈旧、仅本地约束、指代追问、需要登录和平台失败分别覆盖；异常不能被当作无结果。
- 记录内部任务描述、策略修订和分支证据，目标不随外号联想漂移；需要澄清时提出关键问题，不能自信猜测对象。
- “多找一些/重点看评论/继续”有效改变策略，实际工作量受全轮预算控制；旧待确认任务绝不自动补跑。
- 比较字面检索、有限扩展、混合检索的新增有效结果、噪声、已知样例遗漏和成本；语义质量需人工样例核对，不依赖模型自评分。
- 评价任务同时检查信息密度与采样偏差；热门任务检查热度字段依据、采集时间与覆盖范围。

实施更新：单一入口、自动任务判断与默认预算执行已落地；小规模向量缓存采用SQLite，嵌入模型尚待配置。数量扩大量先采用有原话依据的20→40上限，默认总时限180秒，评论补读占全轮额度。新鲜度判断、相关性、评价质量仍需样例验证，不预设准确率或承诺全站覆盖。具体已实现项、配置与限制以[P5交付说明](p5/README.md)为准；本节保留后续设计目标。

## 13. 结果筛选与展示分离（2026-09-22，部分实施）

### 13.1 本次问题与目标

用户请求“收集咒术回战相关的打分贴”，返回中既列出相关帖子，也展示明确排除的帖子卡片。例如《聊聊zzz和圣刃：关于打分权重的问题》被判无关，却仍出现在正式结果里。另有《今天不论术式强度，今天来论论术式的可玩性》被错误归为另一游戏；用户指出其实际讨论的是咒术回战术式，已展示片段也不足以支持“方舟”归因。当前回答还存在“核验10条”与列出11条之间的数量口径冲突。

目标是返回经过筛选的结果集，保留可追溯的筛选记录，但不让排除过程占据主要答案。以下是设计与验收要求，本次仅同步文档，未修改运行代码。

### 13.2 区分证据用途与结果资格

- 内部候选及审阅记录保存全部判断、理由、支持片段和待核实事项，不因前台隐藏而删除原始数据。
- 正式结果集独立维护，明确关联帖子/评论ID、任务相关性、核验状态及用于展示的证据。不得将“被回答引用过”直接视为“应生成推荐卡片”。排除依据也可以是有效证据，但不具备正式结果资格。
- 明确相关项展示标题或评论摘要、原帖链接、可用的时间及回复数；评论链接与原帖链接保持区分。
- 明确无关项默认不展示卡片，不在正文逐条汇报，也不计入相关结果数量。用户要求解释筛选过程时，才从执行详情展开排除理由与原文。
- 待核实项优先在剩余预算内补读上下文。仍不确定且有参考价值时，少量放入独立的“待确认”区域，注明具体不确定点，不混入已确认相关项。没有必要为凑数量展示。
- 间接提及、借用评价体系、帖子本身执行评分等关系必须区分，按当前用户目标判断资格；不能只因出现“打分”一词便保留，也不对某作品或标题设固定排除规则。

### 13.3 逐帖判断，防止跨候选错误归因

核验每条内容时使用该条自身的标题、正文、所属贴吧及必要的父帖/评论上下文。所属贴吧仅是辅助线索，不能单独证明主题。其他候选中的游戏名、人物名和背景不能被直接移植到当前帖子；有跨帖关系时必须有可核对依据。

分别记录“帖子属于什么对象/领域”和“是否满足本次内容意图”，不要把二者混为一个结论。明确判断应附支持片段；证据不足时标为待核实，不能凭“术式”等共享词猜出具体作品。逐字引用检查只能验证文字存在，不能证明解释与归因正确。用户纠正应触发对应条目及其派生分类、摘要和计数重新核验，保留更正记录，不扩大成未经核验的全局规则。

### 13.4 计数与验收

候选数、实际读取数、相关数、待核实数、排除数、展示数分别按独立内容ID计算，不由模型自由编造。读取过片段不等于读完全文；相关性类别应互斥，阅读完整度另行记录。前台按已选择的正式结果生成展示数量；若另有待确认项，单独计数。

验收至少覆盖：无关项被引用用于排除也不产生正式卡片；与另一候选共享术语但领域不同的判断；用户指出误排后的分类与计数更新；间接提及评分与实际评分帖的区分；片段不足时补读或保留不确定；多个片段/来源引用不重复计数。跨领域构造样例，避免只对咒术回战、方舟或特定标题过拟合。另检查默认答案简洁，但用户追问时仍能查看筛选依据。

### 2026-09-24 实施状态：回答与来源展示资格

已在回答读取层根据本轮采集任务持久化的帖子/评论三态核验笔记，对引用来源按快照分成正式相关、待核实和明确排除。来源卡片与回答段落分别分流：只有依据均属于已核验相关快照的段落默认展示；仅以排除项为依据的段落放在筛选详情；混合依据或未审阅依据放在待核实区。评论不能继承父帖的相关性或排除判断；补采后最多独立核验两条评论，必要父帖/父评论仅作上下文，支持引文必须来自当前评论。未核验评论进入待核实区。正式卡片数量由实际相关来源计算，同一实体多片段合并；原始回答、引用和排除原文仍保留，历史无核验笔记的回答沿用旧展示方式。执行详情可查看三态计数、逐条理由和原文片段。对应代码见 `knowledge/presentation.py`、`agent/runtime.py` 和助手页面组件。

执行详情允许用户对已核验的帖子或评论逐条标为相关、无关或待核实，并填写更正理由。服务端只接受当前任务中仍有效且可重新读取的证据，持久保存旧判断、新判断及时间，立即重算三态计数和来源卡片资格；旧回答标记为需要重新核对，不把旧文字静默改写成新结论。此操作不生成全局标题规则，也不触发新的网络采集。

此分流是展示资格控制，不重新证明模型的语义判断正确。帖子/评论核验仍基于片段，不能把未审阅视为无关；用户更正后自动重生成回答、更多评论覆盖、完整阅读不足时的自动补读和真实误排评测尚未实现。测试用例验证相关、排除、待核实、混合引用、父帖引文不得冒充评论依据，以及用户更正后的计数和卡片更新，前端构建通过；因此第13节仍标为部分实施。

## 14. 原文落盘与有界工作上下文（2026-09-22，实施中）

采集按批次立即保存原始帖子、评论及来源关系，包括暂时被判无关的内容；不能只保存初筛相关项。模型摘要和分类是可修订判断，必须关联快照和支持片段，不作为原文替代品。

每批导入后逐帖独立核验，模型只接收当前帖子及本帖必要上下文、用户目标和范围，不携带其他候选的正文或作品归属推断。核验结果落盘，记录相关/无关/待核实与未审阅的区别。重复快照不重复消耗审阅预算；新快照须重新核验。模型调用数、并发和总时限受限，未审阅内容不能被算成无关。

采集与审阅的长期状态留在本地，模型工作上下文只保留目标、已探索方向、证据ID、待核验事项和剩余预算。工具完整返回持久保存，后续调用按需读取原文，主动重建消息而非无限追加。压缩不能删除用户约束，不能让旧摘要获得事实证据资格。

最终从本地按问题检索候选，优先复用已核验记录；支持现有混合检索，未配置嵌入服务时明确退回本地候选与模型语义核验，不宣称已经启用向量模型。候选发现、单帖核验和跨帖汇总分开。读取和引用继续受原文可用性校验约束，无关项不混入正常收集结果。用户追问可重新检索原始候选，不将初筛排除变成永久删除。

首轮实施先保证逐批持久化、逐帖独立核验、可回读的精简上下文和本地结果汇总；动态生成后续查询需继续受原有最多3查询及总配额约束，不能把清空上下文等同于重置预算。验证包括跨帖术语干扰、重复/版本变化、原文失效、上下文缩减后证据恢复、预算耗尽与取消。真实质量需要前后对照，不能将程序测试通过等同于减少幻觉的实验证明。

# 简历上下文优化指标：方法与实测

日期：2026-10-10。脚本：[benchmark_resume_context.py](../../tools/benchmark_resume_context.py)。逐轮结果：[JSON 报告](resume-context-2026-10-10.json)。

## 简历中可使用的表述

> 针对多轮检索上下文膨胀，采用快照持久化、证据 ID 回读与工作上下文重建；六组本地数据离线回放中，较连续追加工具历史，末轮输入上下文字符数平均减少约 64%。

该数字来自现测，不使用“通过多少项测试”替代优化效果，也不声称准确率、召回率、API 费用或线上延迟提高。

## 数据与对照

- 复制已有两份本地采集文件至隔离目录：40 条帖子、149 条评论。源文件哈希保存在 JSON，执行前后核对一致；正式研究数据库未改动。
- 两组固定流程：帖子分页/来源版本/原文回读；帖子分页/来源版本/评论检索/原文回读。每组分别使用每页 5、10、20 条，共六组。
- 每组实际运行当前 `Harness`：6 次工具调用、7 次确定性模型替身调用。替身仅返回指定工具动作和最终格式，不请求外部模型或平台。
- 基线为**连续追加历史的反事实对照**，不是已测量的旧产品版本。初始提示词、每次动作、工具结果及 usage 与当前实现完全相同，只改变旧消息对是否继续保留。
- 当前实现保留目标、简短工作状态、证据 ID 和最新工具结果；旧正文不持续追加。最后一轮回读早期证据，并与首次检索片段逐字核对。
- 指标是所有输入消息 `content` 的 Unicode 字符数，不含 API 消息封装，不是 tokenizer token 数。减少率为 `(基线字符数 - 当前字符数) / 基线字符数`，六组减少率取算术平均。UUID 使用固定随机种子稳定同时间候选的排序。

## 结果

| 回放流程 | 每页条数 | 末轮连续追加 | 末轮当前实现 | 字符数减少 |
|---|---:|---:|---:|---:|
| 帖子版本与回读 | 5 | 21,817 | 9,500 | 56.46% |
| 帖子版本与回读 | 10 | 35,950 | 12,795 | 64.41% |
| 帖子版本与回读 | 20 | 55,647 | 16,267 | 70.77% |
| 帖子与评论检索 | 5 | 19,260 | 9,004 | 53.25% |
| 帖子与评论检索 | 10 | 33,583 | 11,880 | 64.62% |
| 帖子与评论检索 | 20 | 56,817 | 15,772 | 72.24% |

**末轮平均减少 63.62%，累计七次输入的字符数平均减少 42.59%。** 六组均成功回读同一原文片段，持久工作记录没有复制该片段正文，原始文件未变化。

末轮效果比累计效果明显，是因为连续追加的历史随轮数增长；不能把末轮的 64% 写成整次调查 token 或费用下降 64%。样例是固定工具轨迹，不能代表所有真实用户问题，更不能证明相关性判断或结论质量提高。

## 复现

在 `community-agent` 根目录运行：

```powershell
.\MediaCrawler\.venv\Scripts\python.exe tools/benchmark_resume_context.py
```

面试时可说明：工具返回的原文留在可撤销的快照库中，上下文只保留目标、引用标识和当前操作；需要早期内容时重新读取有效证据。字符数节省是工程开销指标，语义质量需要人工标注对照，尚无相应提升百分比。

# 社区检索 Agent：问题与思考

日期：2026-09-18  
更新：2026-09-24（筛选证据与结果展示资格）  
用途：保留需求讨论、设计矛盾与待验证思路，后续持续补充。  
性质：讨论记录，不是已经确定的实现规格，也不代表相关能力已经实现。

实施方案另见 [Agent 集成改进方案](agent-integration-plan.md)。

## 1. 我们希望解决的究竟是什么问题

目标不只是让模型替用户输入关键词，而是帮助用户找到不同表达方式下的相关讨论，理解内容并追溯证据。

当前的基本方案是：

> 理解需求 → 检索候选内容 → 筛选相关内容 → 补充采集 → 分析并回答。

这带来一个根本限制：**如果相关内容没有进入候选集合，后续模型筛选再准确也无法把它找回来。**

因此需要分别考虑：

- **发现能力**：能不能找到用户真正关心的内容？
- **判断能力**：找到后，能不能判断是否相关？
- **回答能力**：能不能根据可靠证据回答，而不把猜测当成事实？

这三者相互关联，但不能用其中一项的效果替代另一项。

## 2. 语义的替代性与关键词漏检

### 用户提出的例子

搜索 CS 职业选手 donk 的相关讨论，用户可能使用：

| 表达类型 | 用户提供的示例 |
| --- | --- |
| 明确名称 | donk |
| 谐音、爱称 | 洞、小洞、小洞大人、洞克 |
| 外号、评价性称呼 | 驴、小驴、世一步、魔王、魔童 |
| 描述性指代 | 17岁天才少年 |
| 相关主题入口 | HLTV Top20 选手榜单 |

这些例子用于说明表达多样性，**不在本文中认定每个称呼都唯一、稳定地指向 donk**。实际使用前需要核对上下文、时间和社区语境。

### 问题

只搜索 `donk`，可能遗漏完全不使用正式名称的讨论。只让模型生成几个普通同义词，也不足以覆盖外号、梗、间接指代和关联主题。

尚待解决：

- 如何发现模型不知道的新称呼？
- 如何区分稳定别名、短期流行梗和一次性的修辞？
- 能否利用已采集的正文、评论和回复关系理解省略的指代？
- 用户提供的别名如何作为线索使用，而不直接视为已经核实的映射？

## 3. 扩大搜索范围与降低相关性的矛盾

关键词太少容易漏检，关键词无限扩展又会带来：

- 大量无关内容，例如单独搜索“驴”或“魔王”。
- 重复结果增加，采集数量增加但有效信息没有增加。
- 更多网络请求、模型调用和等待时间。
- 模型凭联想建立错误关联，导致搜索逐渐偏离最初目标。

因此，目标不是“列出尽可能多的词”，而是：

> 在有限预算内，找到尽可能多的新相关内容，并明确仍可能遗漏什么。

不能只追求返回数量，也不能只追求结果看起来都很相关。过度筛选可能掩盖大量漏检。

## 4. 人物别名与相关主题不能混为一谈

需要区分两种关系：

- **实体指代关系**：某个称呼在特定语境下指向同一个人。
- **主题关联关系**：某个主题可能包含这个人的信息，但也包含其他人。

例如，HLTV Top20 榜单可以作为发现讨论的入口，不能直接当作 donk 的别名。榜单帖子中每个段落、每条评论也未必与 donk 有关。

同样，一条评论同时出现 donk 和“魔王”，可能是在比较两名选手，并不能单凭共现就认定两者相同。

候选映射应记录：来源、原文依据、适用语境、时间范围、歧义，以及待确认状态。不要把一次猜测永久写入“事实库”。

## 5. 一个候选方向：逐步探索，而不是一次性扩展

以下为待验证思路：

1. 明确目标人物或主题，必要时澄清用户究竟想了解什么。
2. 用明确名称和少量有依据的表达获取初始结果。
3. 从结果中发现候选称呼、相关事件和主题入口。
4. 核对候选与目标之间的关系，优先试探少数有希望的查询。
5. 根据新增有效结果调整后续查询。
6. 达到预算或继续搜索的收益明显下降时结束。

对于高歧义表达，可以尝试与游戏、赛事、战队等语境组合；但平台未必严格执行组合词条件，仍须核对实际结果。

不能声称此流程能够找到所有相关内容。它只是一个需要通过样例验证的改进方向。

## 6. 用什么判断一个查询是否值得继续

候选观察指标：

| 指标 | 用途 |
| --- | --- |
| 返回数量 | 判断是否得到候选，不等于有效信息量 |
| 重复比例 | 判断是否只是反复找到同一批帖子 |
| 新增相关帖子数 | 判断是否扩大了有效覆盖范围 |
| 新增相关观点或事件 | 判断是否提供了新的信息，而非重复表述 |
| 不确定结果比例 | 观察别名歧义、证据不足等问题 |
| 耗时与模型用量 | 衡量搜索和分析成本 |

需要保留少量探索预算，避免早期高收益查询占据全部资源，使系统永远困在最初发现的几个表达中。

尚未确定具体评分公式、阈值和预算分配策略。相关性判断本身也可能出错，不能完全依赖模型给出的分数。

## 7. 停止条件与结果完整性

可以考虑的停止条件：

- 达到用户授权的时间、查询数、帖子数或模型调用预算。
- 连续若干轮没有新增有价值的内容。
- 已获得足够证据回答当前问题。
- 登录、网络或平台限制导致无法继续。

“足够回答问题”和“找全所有讨论”是不同目标。停止时应说明查询范围、实际使用的表达、采集限制和未解决的问题。

**未找到结果不能直接推导目标内容不存在。** 同样，前十条没有某篇帖子，也不能证明平台完全不支持该表达。

## 8. 本地语义检索的价值与边界

本地语义检索可以帮助发现：已采集内容中没有直接写出目标名称，但上下文与目标有关的片段。

它不能帮助发现从未进入本地数据的帖子。因此，向量检索不能单独替代候选发现，也不能自动解决平台搜索覆盖不足。

可以组合的候选来源包括：多个关键词查询、指定帖子、作者主页、项目支持的指定贴吧采集，以及已经采集内容中的关联线索。

每种来源仍须明确预算和覆盖范围，不能默认无限采集。

## 9. 帖子相关，不代表每条评论都相关

现有采集曾出现：帖子正文只顺带提到“打 cs”，于是其下大量人际纠纷评论也被采集。这说明需要区分：

- 帖子字面包含查询词。
- 帖子主要讨论目标主题。
- 某条评论是否围绕目标主题。

另一方面，没有关键词的回复也可能高度相关。例如“确实，这次降得太狠了”需要结合原帖或父评论判断。

候选设计是保留原始帖子与评论关系，在展示层提供“全部已采集评论”“字面匹配评论”“主题相关评论”，不直接删除被模型判为无关的数据。

## 10. 来源字段不能代替匹配证据

`source_keyword` 记录采集时使用的搜索词，不是原文内容，也不是主题相关性的保证。

后续应分开展示：

- 通过哪个任务、哪个查询找到。
- 在标题、正文或评论的什么位置命中。
- 为什么判断其与目标人物或主题相关。

匹配检查必须排除程序附加的来源标签，否则会出现“因为自己写入关键词，所以判断结果匹配”的循环。

## 11. 如何验证改进，而不是只看演示效果

建议建立一组人工核对的样例，覆盖：正式名称、别名、歧义称呼、间接指代、相关主题、无关共现和依赖父评论的回复。

比较至少三种方式：

1. 只搜索明确名称。
2. 一次性使用固定扩展词列表。
3. 根据结果逐步探索、验证和调整查询。

同时观察新增相关结果、无关结果、漏掉的已知相关样例、重复比例及成本。平台全量内容不可知时，只能报告样例范围内的覆盖情况，不能声称测得了全平台召回率。

需防止循环评估：同一个模型既负责筛选，又独自判定自己的筛选效果，会掩盖错误。关键样例应人工检查，保留原文依据。

## 12. 当前倾向与待讨论问题

### 当前倾向

- 不采用无限制关键词扩展。
- 第一版允许用户提供已知称呼，助手提出候选并记录依据。
- 先用明确名称建立种子结果，再小批量探索。
- 原始数据、搜索来源、实体判断和分析结论分开保存。
- 用预算和新增有效结果控制继续搜索的范围。

### 待讨论

- 第一版优先解决人物检索，还是产品、事件等主题检索？
- 别名需要多少依据才可以自动用于后续查询？
- 哪些歧义需要问用户，哪些可以作为候选继续探索？
- 不同平台、社区和时间段的称呼是否分别维护？
- 对于“全面了解一个人”和“回答一个具体问题”，预算如何区别？
- 如何向用户展示覆盖不足，而不让回答变成长篇免责声明？
- 本地已有数据与实时采集如何权衡，何时需要更新？

后续新增想法时，优先记录具体例子、矛盾、假设和验证办法，再决定是否纳入实施方案。


## 13. 称呼歧义会不会把搜索目标带偏

### 用户提出的问题（原文保留）

另一个问题,依旧拿donk举例，通过不同的称呼延伸出来的搜索范围也不一样:如果我的关键词不是donk，而是小驴，那可能从cs选手延申到动物上，搜索范围从电竞延申到农牧业相关，感觉这就很不好。不过这可以通过对助手进行更多细致解释介绍弥补，但也需要提示词带给助手的约束能力足够强才行，这应该是harness上的问题，保证约束力的同时不要丧失所有发散性，做到一定的平衡。

### 问题的进一步区分

这里不只是结果数量变多，而是查询扩展可能改变系统对任务目标的理解：

```text
希望发生：目标始终是 donk → 用“小驴”等表达寻找同一人物的讨论
需要避免：donk → 小驴 → 驴 → 动物 → 农牧业，目标随联想不断改变
```

应固定的是用户已经明确的目标，不是固定某一个查询词。用户主动改变目标时可以更新；不能因新查询词具有其他含义就自动改写目标。

如果用户最初只有“小驴”二字且没有上下文，无法确定其指向选手还是动物。此时应澄清，而不是让强提示词强行猜测。若此前对话已明确在讨论 donk，就应利用该上下文，不必反复询问。

### 为什么不能只加强提示词

这是目标识别、检索策略和 Harness 共同承担的问题：

- 提示词指导模型保持目标和提出有依据的扩展。
- 工具接收明确的目标、语境与查询条件，并返回实际执行结果。
- Harness 保存原始目标、查询分支来源和预算，防止模型输出直接覆盖目标或无限递归扩展。
- 结果核验检查内容是否真的关联回目标，而不是仅出现某个候选称呼。

Harness 能保证执行流程受控，不能单独保证每次语义判断正确。“要求提供依据”不等于“依据必然成立”；证据的真实性和关联仍需检查。

### 约束与发散的候选平衡方式

把检索分为主线和有限探索。主线优先使用明确名称、有依据的别名和关联事件；探索允许试用歧义表达或间接主题，但先取小批量结果，核对关联后再决定继续。

不同分支都关联到同一个目标，记录查询来源、关系假设、支持或反对的证据，以及继续或停止原因。不要因为“魔王”与 donk 共现，就把所有关于魔王的内容都纳入范围。

约束也不能过度简化成“每条结果必须出现 CS”。有些相关讨论只使用外号，领域语境来自贴吧名称、原帖或父评论。应检查可追溯的关联依据，而不是只检查固定领域词。

平台搜索能力是另一层边界：即使输入“小驴 CS”，也不能假定平台会严格限制领域。系统可控制查询选择、预算和结果验收，不能承诺平台完全服从搜索意图。

### 尚待验证

- 什么样的关联证据足以把探索分支提升为主线？
- 对新称呼至少试探多少内容才有意义，如何控制无效探索成本？
- 如何保留必要的上下文，避免把简称、反讽或多人比较误认成别名映射？
- 如何量化目标漂移，同时避免把跨主题但确实相关的内容全部排除？
- 如何记录用户目标修订，并使旧查询和证据仍能追溯到当时的目标？

当前原则：**固定已明确的目标，允许查询表达变化；允许有限试探，但分支扩展需要说明关联，并接受结果核验。** 具体阈值和策略尚未定案，相关设计已同步到改进方案的查询扩展、Harness 职责和阶段验收部分。

## 14. P4能调度爬虫，不等于已经懂得如何调查问题

P4把自然语言规划、现有爬虫、导入和引用回答串起来，底层仍依赖平台搜索。同样查询和参数下，它不会天然比普通采集发现更多相关内容。模型已经能够生成保守查询词，但查询生成、别名发现、语义筛选和分析策略是不同能力，不能把其中一个演示成功当作全部实现。

用户期待的是助手理解问题并组织调查，而不是把关键词配置换一种展示形式。2026-09-20的模式选择和计划确认是过渡交互；下文保留当时提出的要求，当前实现状态以[改进方案](agent-integration-plan.md)和[P5记录](p5/README.md)为准。

## 15. 向量检索能补什么，不能补什么

用户希望引入语义向量，减少同义表达造成的漏检。方向是关键词与向量混合检索，而不是取消字面检索：明确名称适合准确匹配，不同措辞的体验和原因适合语义候选召回，之后仍要读取原文核验。

两条边界必须保留：

- 未采到的内容不在本地索引中，向量库不能补回平台搜索没有返回的帖子；需要同时改进候选发现。
- 相似度不是同一实体或事实成立的证明。“小驴”与donk的关系仍要结合社区、游戏、事件和时间判断。

小幅扩展宜先用明确名称，再验证少量候选外号；高歧义称呼可以尝试增加CS等语境词，但不能只留下含CS的原文。新增相关内容多的分支继续，重复或无关内容多的分支停止。模型记忆提出的别名只是线索，不能免证据核验；“天才少年”与榜单主题也不应被登记为稳定别名。

待验证：相同预算下混合检索是否增加有效内容，是否增加跨领域噪声；嵌入成本、切片策略及上下文缺失如何影响结果。还需继承原有来源删除与引用失效规则，不能让向量索引保留不可验证的旧内容。

## 16. 提问式查询：评价信息密度与代表性不是一回事

用户的例子是：“某某游戏最近在玩家群体里的评价如何？”只搜游戏名会得到大量攻略、组队、交易等内容，并非都属于评价。不能要求用户提前写出足够专业的搜索提示词；助手应识别这是一个分析任务。

候选方法是拆分玩法、更新、性能、付费、运营等观察方向，围绕这些方向收集并识别评价，再根据实际内容调整。保留少量宽泛搜索，避免预设议题把真正的新问题排除。攻略帖下也可能有评价评论，评论可能需要原帖或父评论才能理解，不能仅凭帖子类型整批丢弃。

这里的矛盾是：定向搜索提高信息密度，也可能放大采样偏差。只搜“差评”“退坑”会偏负面；只看高回复帖子容易把争吵当主流；同一用户重复发言不能等同于多个玩家支持。评价立场与主题相关性也应分开，相关但没有明确态度的内容不必强行归为好评或差评。

回答应呈现认可点、批评点、原因、分歧和证据，并限定时间及采集社区。贴吧样本不能直接代表全体玩家，“最近”需要落实时间范围，“态度变化”需要可比的前后样本。没有代表性依据时，不给出貌似精确的总体满意度。

## 17. 任务分类应在助手内部，不增加功能按钮

用户接受新增评价分析，但明确不希望出现“口碑分析/趋势分析”等外显入口。内容查找、原因分析、口碑归纳、变化比较只是内部策略，可以组合，也可以根据证据修正。

模型根据当前问题和会话上下文生成结构化任务描述：目标、时间、证据需求、处理方向和数据策略。Harness验证并执行，不用几个词硬编码决定全部行为。对于“为什么很多人在骂更新”，应先验证问题前提；分类结果不构成真实证据。

关键目标缺失时才澄清，已在会话中明确的内容不反复询问。自动判断无法保证每次正确，因此要保留策略修订记录和对话纠正路径，不能把一次分类永久锁死。

## 18. 本地与联网也应自动判断，不能让用户替助手选工具

用户进一步明确：“查询已有数据/联网采集”也不应成为手动模式。理想界面是一个助手：提问、简短进度、回答和停止；查询词、分类、采集数量等放入可展开执行详情，原手动爬虫仅为高级备用入口。

应根据证据需求、时效和本地覆盖选择本地、联网或组合路径。“刚才这些帖子说明什么”优先会话材料；“最近口碑如何”检查新鲜度后决定是否补采；用户要求“只看已有数据”时不得自行联网。本地存在命中，不代表足以回答；本地无命中，也不等于一定要联网或全站不存在。

把按钮隐藏并不等于完成自动化。真正要补的是数据充分性判断、任务调度、预算核算、失败处理和目标保持。用户不应每轮提供工具参数，系统仍必须承担执行约束。

## 19. “等待确认”配置卡同样背离对话目标

用户输入“收集贴吧一些热门的打分贴”后，当前页面展示“在线采集·等待确认”、查询词、帖子/评论数、总时限和确认按钮。用户明确希望移除此类必经表单，设置默认查询范围，扩大时通过自然语言表达。

讨论中的建议默认上限：每轮3个查询、合计20个候选帖子；按需最多3帖各20条一级评论；总时限180秒。**这些是待落实的建议值，不是当前实现参数，也不是最低采集量。** 模型调用、重试、重复请求同样应受控，硬上限及“多找一些”的具体增幅尚待设计。

在默认预算内，提问即可触发内部规划和执行，不再要求批准每组关键词。“最近三个月”调整时间、“重点看评论”调整证据分配、“继续”应考虑已有结果；范围扩大不能被当作无限授权。只在登录、关键歧义或超出可执行范围等必要环节打断。历史待确认任务保持不运行，不能在升级或刷新后突然补跑。

此例还体现理解差距：生成“打分贴”未处理“热门”。可有限尝试“打分帖/评分帖”等表达，核对帖子类型，并利用回复量、发布时间等可用指标比较。回复多不等于赞同多；采集时统计可能变化；缺失数据不能当0。结果应表述为“本次检索范围内较热门”，而非贴吧全站热榜。

## 20. 最新共识与验证重点

已明确的产品方向：单一对话入口、内部判断任务及本地/联网路径、默认预算直接执行、自然语言调整范围、简短进度与可停止、证据可追溯。具体数值、模型与阈值仍是工程待定事项。

验证应分别检查：

- 用户无需选模式或填写参数，能否完成具体任务；仅本地限制、会话追问、模糊目标和登录失败是否正确处理。
- 扩大范围是否增加有效信息，而非只增加重复和噪声；预算是否覆盖所有分支，旧待确认任务是否保持不运行。
- 关键词扩展、向量检索、评价分析分别带来什么增益，不能把模型自评分当作效果证明。
- 评价内容的信息密度是否提高，采样偏差是否被识别；热门与趋势结论是否有真实字段和可比证据支持。

实施对应 [改进方案第12节](agent-integration-plan.md#12-最新需求单一助手与内部自动判断2026-09-21)。以上保留讨论背景；后续实现情况见下面的实施跟踪，不将设计目标整体视为上线能力。

## 22. 筛选过程不等于用户要的结果（2026-09-22）

本次“收集咒术回战相关的打分贴”已有不少有效结果，但暴露了两个独立问题：一是明确无关的《聊聊zzz和圣刃：关于打分权重的问题》仍被展示；二是“术式可玩性”帖被错误归为方舟，用户指出它实际讨论咒术回战术式。不能因为最终把帖子展示出来了，就忽略分类错误。

无关内容进入结果卡片，反映出筛选证据与正式结果资格没有充分区分。助手可能为了说明排除理由而引用某帖，但“引用过”不意味着“推荐给用户”。对收集类请求，默认应展示筛选后的内容，无需逐条汇报噪声；筛选记录应保留在内部或执行详情，用户需要时再展开。隐藏排除项不是删除原始数据，也不意味着缺少可追溯性。

错误归因方面，展示片段没有支持“方舟”的依据。相邻候选恰好有“六星术士”内容，跨候选背景串用是一种可能原因，但目前未核查完整执行轨迹，不能把猜测写成已确认根因。应逐帖使用自己的标题、正文、所属贴吧和必要上下文；既不能借其他帖子的作品名称下结论，也不能单靠所在吧证明归属。

引用原文真实与理解原文正确是两层检验。字面存在检查挡不住语义误读；证据不足时，“待核实”比编造一个具体作品名更合适。对象归属与是否满足本次内容意图也应分别判断：提到打分帖、借用某作品的评分体系和真正给该作品对象评分，不必具有相同的结果资格。规则应适用于不同领域，不对本次标题建立特例。

当前共识：明确相关进入正式结果；待核实优先补读，有必要才单独少量展示；明确无关默认隐藏，不逐条解释。用户主动追问筛选过程时再提供排除依据。用户纠正应促使原条目的分类、摘要和相关统计重新核验，不能只修改一句描述。

此外，回答中的“候选11条、核验10条”与展示内容数量出现冲突，说明计数不应由模型随意组织。候选、已读、相关、待核实、排除和展示要区分；读过片段不是读完全文，多个引用片段也不是多个帖子。主要答案应简洁说明实际展示内容及必要范围限制，而非堆叠审计式说明。

本节保留2026-09-22的讨论结论；展示分流已有部分实施，真实误归因仍需评测。对应实施拆解和验收见[改进方案第13节](agent-integration-plan.md#13-结果筛选与展示分离2026-09-22部分实施)。

## 23. 本地资料库承担长期记忆，上下文承担当前工作（2026-09-22）

用户提出边采集边保存本地，腾出上下文继续收集，最后本地语义检索。该方向有助于控制上下文规模与纠错，但保存文件本身不会释放模型上下文，Harness需要主动重建消息。现有项目已有原文落盘，缺口在于逐批核验、工作状态管理和避免整批文本反复进入上下文。

原文应全部保留，分类与摘要允许修订。只存“相关”内容会固化误排；只存错误摘要可能持续强化错误。向量相似仅帮助发现候选，不能证明作品归属。针对“咒术术式/方舟术士”问题，更直接的办法是先在单帖自身上下文中判断，再汇总核验结果，避免借用其他帖子背景；尚不能确认历史误判由长上下文导致。

采集过程中也可以查询本地覆盖与待核实事项，不必等全部结束。需要区分已读片段、已读全文、已核验和未审阅；预算不足时保留未完成范围。清空上下文不重置采集或模型预算。恢复证据须回到原文，并检查来源是否仍有效。没有嵌入配置时不能称已完成向量检索部署，模型语义核验与向量召回是不同能力。

对应[改进方案第14节](agent-integration-plan.md#14-原文落盘与有界工作上下文2026-09-22实施中)。本节记载设计依据，实际效果以后续实现与测试记录为准。

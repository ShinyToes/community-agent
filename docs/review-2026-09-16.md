# 学籍管理系统审查与修复

日期：2026-09-16。范围：复制后的 `student-management-agent`；未修改原数据库实验目录，未连接原 MySQL、未运行原初始化或导入脚本。

## 结论

**不用推倒重来。** Flask 工厂、蓝图、模型、模板和服务层划分能够继续使用。主要问题集中在权限边界、事务提交位置、输入校验、初始化安全，以及 Python 与 MySQL 两处业务逻辑不一致。重写框架无法自动解决这些问题。

本轮保留 Flask + SQLAlchemy + MySQL，修复明确缺陷并补回归测试。没有新增 Agent、切换框架或拆微服务。

对应实现重点：

- `app/utils/security.py`、`app/auth.py`：身份、对象权限、跳转和旧上传入口。
- `app/services/file_service.py`：存储边界与文件事务生命周期。
- `app/services/grade_validation.py`、`app/blueprints/grade_bp.py`：分数、权重与成绩批次。
- `app/utils/audit.py`：审计不提交事务；MySQL 连接取出时清空旧操作者变量。
- `app/blueprints/enrollment_bp.py`、`sql/02_procedures.sql`：统一选课和重选路径。
- `tests/`：HTTP 级权限/CSRF、服务与事务测试、模板检查。

## 业务规则变化，需要知晓

1. 只支持管理员、学生两种实际角色。旧代码中名为教师/辅导员的分支没有完整授权设计，不默认授予管理权限。
2. 成绩必需分项未齐时不发布总评；零权重分项允许留空。总评或补考达到 60 记已通过，缺考未通过，缓考保持在修。绩点依旧按原总评计算。
3. 不再为了重修而自动把旧“未通过”记录改成“退课”，避免改写成绩历史。同一开课实例的重修如何处理仍需业务确认。
4. 时间冲突限定同学年同学期，但仍采用 schedule 整串相等，不能识别“周一1–2节”与“周一2–3节”的部分重叠。
5. 学生只可为本人的待审批转专业申请写附件；学生档案、奖惩、体检附件由管理员维护。
6. 审计记录中操作者 0 表示无登录操作者的数据库维护操作，不再默认冒充管理员 1。
7. 原实验文件、Git 历史、旧 .env 和旧上传文件保留；新的运行配置与文件存储已经分离。

## 验证结果及边界

- 在本机新建项目专用 `.venv-dev`，使用 Python 3.13 与独立依赖。
- SQLite 内存数据库 + 临时文件的回归测试覆盖：越权、CSRF、跨站跳转、禁用会话、附件清理/回滚、转专业冒用与重复申请、已审批状态保护、成绩批次失败回滚、缺失行、零分/零权重、成绩状态、学籍关联、存储型 HTML 转义、禁止连接原库等。
- 测试使用虚构学生，不需要读取原数据库或真实附件。
- 已检查所有 Jinja 模板可编译、所有 POST 表单含 CSRF；完成 Python 编译与依赖一致性检查。
- 存储函数在部分测试中被替代；审计辅助函数用 mock 检查“设置操作者而不 commit”；选课路由测试只证明调用统一入口。**这些不是 MySQL 集成测试。**
- 本机未发现可用 MySQL 服务，Docker daemon 不可用；未验证真实存储过程执行、触发器、行锁、并发、SQL 初始化顺序及浏览器全流程。
- 旧 SQLAlchemy Query.get 调用仍产生弃用警告，后续可逐步统一成 db.session.get，不影响本轮测试断言。

准确的本轮测试数量和最终检查结果记录在 `progress.md`。

## 采用的官方依据

- [Flask-WTF：CSRF](https://flask-wtf.readthedocs.io/en/1.2.x/csrf/)：全局保护、隐藏表单字段和 AJAX 请求头。
- [Flask：安全注意事项](https://flask.palletsprojects.com/en/stable/web-security/)：HTML 转义、上传响应、Cookie 和响应头。
- [SQLAlchemy：Session Basics](https://docs.sqlalchemy.org/en/20/orm/session_basics.html)：区分 flush 与 commit，维持事务边界。
